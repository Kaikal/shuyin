# 疏音 · 第二阶段前置调研报告

> 调研对象：工作区 `音源/` 目录下的两个洛雪音源脚本
> 调研方式：静态阅读 + 桩 `lx` 运行时捕获 + 极简沙箱加载 + **真实网络端到端取链**
> 结论先行：**两个音源都只做 `musicUrl`，没有任何搜索/歌单 action → 必须走「路径 A」自建平台 API 层**。
> 且实测下来 **`K×H测试` 可用、`长青SVIP` 已基本失效**（详见第 4 节）。

## 3. `request` action 支持范围

用同一套桩逐个 action 试（`wy`，`{type:'320k'}`）：

| action | K×H | 长青 |
|---|---|---|
| `musicUrl` | ✅ | ✅ |
| `lyric` | ✅ 返回 `{ lyric, tlyric, rlyric, lxlyric }` | ❌ `不支持动作:lyric` |
| `pic` | ✅ 返回封面 URL 字符串 | ❌ `不支持动作:pic` |

| `songList` | ❌ | ❌ |
| `playlist` | ❌ | ❌ |
| 其他/空 | ❌ `未知事件: X` | ❌ `不支持动作:X` |

**判定：两者都只负责 `musicUrl`，没有任何搜索或歌单能力 → 第 3 节「路径 A」是唯一路径，不需要向你确认切换路径 B。**

附带收获：`K×H` 运行时还能给 `lyric` / `pic`，虽然它没在 `actions` 里声明。这两个可以作为在线歌词/封面的**补充来源**（但主来源仍建议用平台 API 层，因为音源可能不覆盖全部平台）。

## 4. 宿主 API 依赖面

两个脚本解构的都是同一小组：

```js
const { EVENT_NAMES, request, on, send, env, version } = globalThis.lx
```

| 宿主 API | K×H | 长青 |
|---|---|---|
| `EVENT_NAMES.request` / `inited` | ✅ 用 | ✅ 用 |
| `on` / `send` | ✅ | ✅ |
| `request(url, opts, cb)` | ✅ | ✅ |
| `env` / `version` | 解构了但未实际使用 | 同 |
| `lx.utils`（crypto / buffer） | ❌ **完全没碰** | ❌ **完全没碰** |
| `lx.currentScriptInfo` | ❌ | ❌ |
| `Buffer` / `atob` / `require` / `process` | ❌ 不需要（注释明确说沙箱没有，自己写了纯 JS base64） | ❌ 不需要 |

`request` 的调用形态（两者一致）：

```js
request(url, { method, timeout, headers, body }, (err, resp) => { resp.statusCode, resp.headers, resp.body })
```

**关键坑（实测踩到）**：`resp.body` 必须是**字符串**。我第一版宿主把 body 解析成对象再给，K×H 兼容（它自己判 `typeof body === 'string'` 才 parse），但长青直接 `JSON.parse(resp.body)` → 抛 `"[object Object]" is not valid JSON`。所以宿主 `lx.request` 一律返回原始文本，让脚本自己解析。

## 5. 加载测试结果

三种环境都试过：

| 环境 | K×H | 长青 | 说明 |
|---|---|---|---|
| Node 全量环境 | ✅ inited | ✅ inited | 基线 |

2. **每次 `musicUrl` 之前先 GET `https://www.97abc.com/count.php?id=lx-yuningxi-cq`** —— 作者的调用统计。它只发 id，不带我们的数据，但确实有外联。

## 6. 可播性实测（本机真实网络，不是桩数据）

用平台搜索拿到真实歌曲，再喂给两个音源取链，最后**真的去下前 4KB 判断是不是音频**。

测试曲目：稻香 / 周杰伦。

| 平台 | 音源 | 结果 | 耗时 | 证据 |
|---|---|---|---|---|
| `wy` | **K×H** | ✅ | 215~235 ms | `http://m801.music.126.net/...` → `206` `audio/mpeg` magic `49443304`（ID3） |
| `wy` | 长青 | ❌ `无可用播放链接` | 223 ms | — |
| `kw` | **K×H** | ✅ | 465 ms | `http://car-er.kuwo.cn/...` → `206` `audio/mpeg` `audio: true` |
| `kw` | 长青 | ❌ 请求超时 | **12,005 ms** | — |
| `kg` | **K×H** | ✅ | 491 ms | `http://fsandroid.tx.kugou.com/...` → `206` `audio/mpeg` `audio: true` |
| `kg` | 长青 | ❌ `无可用播放链接` | 129 ms | — |

**长青为什么全灭**（读了它的请求体才看明白）：它把 `{source, rid, level}` POST 到 `https://musicserver.haitangw.cc/v1/music/resolve-url`，也就是**海棠的第三方代理**。而 K×H 的更新日志第 1 条写的就是「清除海棠 API (已失效)」——两边互相印证。

> 这份「长青只走一个代理」的判断也解释了它的字段要求：`rid` 对 `kg` 取 `hash`，对 `wy`/`tx`/`kw` 取 `songmid`。网易云搜索结果里没有 `songmid`，所以即使海棠活着，wy 这条也大概率取不到。

**K×H 的链路结构**（顺带记下来，方便排查）：每个平台一组 API，组内并行、组间串行 + 音质降级链。
- 直连平台：`u.y.qq.com` / `ut.y.qq.com`、`171.80.3.149:3036/song/url/v1`（网易云，带 MUSIC_U cookie）
- 第三方免费节点：`api.cxzja.cn`、`api.chksz.top`、`api.yaohud.cn`、`api.ygking.top`、`yy.zddyr.top`、`api.yunmge.com`、`oiapi.net`、`v.yuafeng.cn`、`api.xcvts.cn`、`mcp.nianxinxz.com`
- 搜索兜底：拿 `name + singer` 去第三方节点搜

**⇒ 降级链的现实**：现在真正可用的只有 1 个成员（K×H）。长青必须仍然被加载和展示，但在 UI 上应标「故障 / 不可用」，且**不能排在链首**——它失败一次要 12 秒。

## 7. `musicInfo` 字段要求（决定搜索层要透传什么）

两个音源取 id 的偏好不一样：

| 平台 | K×H 取 id 顺序 | 长青取 id |
|---|---|---|
| `wy` | `songId` → `id` → `songmid` | **`songmid`** |
| `kw` | `songId` → `rid` → `musicId` → `id` | **`songmid`** |
| `kg` | `hash` → `FileHash` → `fileHash` → `songId` | **`hash`** |
| `tx` | `songmid` → `strMediaMid` → `mid` → `songId` | **`songmid`** |
| `mg` | `copyrightId` → `songId` | 不支持 |

结论：`SearchSong.raw`（平台原始对象）**必须原样透传给音源**，只给归一化后的 `id` 会有一半场景取不到链。另外 K×H 的若干兜底分支会拿 `name` + `singer` 去搜索，所以这两个字段也必须带。

## 8. 平台 API 层可达性横评（本机实测）

这一层和音源无关，是第二阶段要自己移植的。五个平台全部试了一遍：

| 平台 | 搜索 | 歌单搜索 | 歌单详情 | 歌词 | 封面 |
|---|---|---|---|---|---|
| `wy` 网易云 | ✅ 5/5 条 | ✅ 5 个 | ✅ 144 首（含 `ar` / `dt` / `album`） | ✅ 970 字 LRC | ✅ `p2.music.126.net` |
| `kw` 酷我 | ✅ 5/5 条 | ✅ 5 个（`DC_TARGETID`/`name`/`nickname`/`pic`/`songnum`/`playcnt`） | ⚠️ `nplserver` 只回标题、`musiclist` 空；`www` 版要 `csrf` cookie | 待接 | 搜索已带 `pic` |
| `kg` 酷狗 | ✅ 5/5 条（`FileHash`/`SongName`/`SingerName`） | ⚠️ `mobilecdn` 404、`msearchcdn` 不通 | ⚠️ 同左 | 待接 | 待接 |
| `mg` 咪咕 | ✅ 20 条（`id`/`copyrightId`） | 未测 | 未测 | — | — |
| `tx` QQ | ✅ 10/10 条，分页正常 | ✅ 5 个（`songlist.list`，`dissid`/`dissname`/`imgurl`/`song_count`/`creator`） | ✅ 99 首（`fcg_ucc_getcdinfo_byids_cp`） | 待接 | 由 `album.mid` 拼 `T002R300x300M000{mid}.jpg` |

**`tx` 的坑与解法**（花了最多时间这一处）：`musicu.fcg` 的 `DoSearchForQQMusicDesktop` 在 `comm.ct='19', cv='1859'` 下**中文查询返回空列表**（`req_1.code=2001`，但 `meta.sum=1002` 说明服务端知道有 1002 条，只是不下发）；换成 **`comm: { ct: '11', cv: '0', uin: '0', format: 'json' }`** 之后中文、分页、`num_per_page` 全部正常。加 `sign` 没用、加 `guid`/真实 `uin` 反而变 2001、换 `u6.y.qq.com` 报 2000。旧的 `c.y.qq.com/soso/fcgi-bin/client_search_cp` 已经彻底返回 0 条（`code:0` 但 `song.list` 空），不要再用。

**⇒ 四个平台都能做**，按你的要求 `wy` / `kw` / `kg` / `tx` 全上。分工建议：

- `wy`：搜索 / 歌单搜索 / 歌单详情 / 歌词 / 封面 —— 能力最全，作为主力
- `tx`：搜索 / 歌单搜索 / 歌单详情 —— 第二主力
- `kw`：搜索 / 歌单搜索（详情暂缺，UI 上该平台歌单卡片不提供"进入详情"）
- `kg`：搜索（歌单与详情暂缺）

歌单详情至少跑通两个平台（`wy` + `tx`），满足验收清单。

| 项 | 现状 | 第二阶段怎么接 |

| 导航 | `Shell.tsx` 里是 `.sb-item`（本地音乐 / 导入歌单 / 设置），`Page` 类型为 `'library' \| 'playlist' \| 'settings'` | 加 `'search'` 到 union + 一项 `.sb-item`；`KEYS.uiPage` 的恢复逻辑要同步 |
| 设置存储 | `lib/settings.ts` 的 `KEYS` 是扁平字符串表，值走 tauri-plugin-store | 按同样格式加 `sources.dir` / `sources.enabled` / `playback.quality` / `search.history` / `search.platforms` |

| HTTP 代理 | 无 | 两个选择：加 `tauri-plugin-http`（要配 scope），或自己写一个 `net_request` Rust 命令。**建议后者**——`play_url` 本来就要在 Rust 侧拉流，顺手复用 |

## 10. 风险

1. **长青基本不可用**，降级链实际只有 K×H 一个成员；且它失败一次要 12s。若照提示词写的「超时 15s、按音源列表顺序」直接做，第一次播放可能先干等 12 秒。建议：单源超时收紧到 8s，并且**按最近成功记录排序**，故障源靠后。
2. **K×H 依赖约 10 个第三方免费节点 + 1 个裸 IP**，全部随时可能挂。好消息是它自带组内并行 + 组间串行 + 音质降级，目前 wy/kw/kg 三条路都跑通了；坏消息是这类音源的可用性会随日下滑，UI 上要把「换源」做成常驻能力而不是异常分支。
3. **长青有外联统计**（97abc.com）和版本检查；建议在音源管理页展示「该音源会外联」。
4. **`mg` 只有 K×H 支持**，做咪咕等于单源，风险同上。
5. **`tx` 搜索需要签名**，若必须支持要额外移植洛雪的 sign，工期另算。
6. **`play_url` 的流式解码**：rodio 的 `Decoder` 需要 `Read + Seek`，HTTP 响应体不是 Seek。两条路——(a) 自己实现基于 Range 的 `HttpRangeReader: Read + Seek`（约 80 行，能边下边播、能拖动进度，推荐）；(b) 先缓存到临时文件再播（简单，但起播慢、远距离 seek 要等）。
7. **音质切换要保持进度**：换链后 `seek` 回原位置。注意 K×H 会**静默降级音质**（请求 320k 实际给 128k），所以 UI 上「当前音质」不能只显示用户选的，最好把实际返回的档位也标出来（可从 URL 后缀/码率判断，或干脆标注「已降级」）。

## 11. 已确认的决策（2026-10-23）

1. **平台**：`wy` + `kw` + `kg` + `tx` 四个全做（tx 的匿名过滤已用 `ct:11/cv:0` 绕过，不需要移植签名模块）。
2. **范围**：本轮**只做桌面端**，移动端下一版。
3. **音源目录默认值**：`%APPDATA%\cn.shuyin.player\sources`（用户目录），仓库里那两份不自动加载，首次进设置页由用户点选目录。
4. **降级链**：`长青` 排在 `K×H` 之后，并且单源超时从 15s 收紧到 **8s**（长青 kw 失败一次要 12s，会让首次播放干等）。UI 上长青标「故障 / 可用性未知」。
